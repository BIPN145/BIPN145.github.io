# Contributing to the BIPN 145 Lab Manual

This repo builds a [Jupyter Book](https://jupyterbook.org) that's published automatically to [bipn145.github.io](https://bipn145.github.io). You do **not** need to install Jupyter Book, Python, or anything else on your computer to contribute — a GitHub Action rebuilds and publishes the site automatically whenever changes are merged.

## The basic workflow

1. **Make your edits.**
   - For small changes (fixing a typo, editing a paragraph), the easiest way is to click the pencil icon on any `.md` file directly on GitHub.com — no local setup needed.
   - For bigger changes (new pages, notebooks, images), clone the repo and edit with any text editor / VS Code. You still don't need Jupyter Book installed just to edit files.

2. **Save your changes as a Pull Request (PR), not a direct push to `master`.**
   - If you edited on GitHub.com, it will offer to create a new branch and open a PR for you — say yes.
   - If you're working locally:
     ```
     git checkout -b my-change-name
     git add <the files you changed>
     git commit -m "Describe what you changed"
     git push -u origin my-change-name
     ```
     Then open a PR on GitHub from that branch into `master`.

3. **Check the automated build.** Every PR automatically triggers a "Build and deploy Jupyter Book" check. Wait for the green checkmark — it means the book compiles cleanly with your changes (a broken link in `_toc.yml`, invalid MyST syntax, a missing image file, etc.). If it's red, click "Details" to see what broke and fix it before merging. Note this check does **not** re-run notebook code (see below) — it only confirms the book itself builds.

4. **Get it reviewed and merged.** Once the build check passes, Ashley (or whoever has write access) reviews and merges the PR. **As soon as it's merged into `master`, the live site rebuilds and republishes automatically within a couple of minutes** — no manual build/deploy step required from anyone.

## A few things worth knowing

- **You never need to touch the `_build/` folder.** It's regenerated by the Action and is not tracked in git. If you see it locally after building, ignore it (it's in `.gitignore`).
- **Notebooks are never re-run during the build.** Every `.ipynb` page always displays whatever cell outputs are already saved inside the file — the build just reads and displays them as-is, it doesn't execute any code. This means if you edit a notebook's code, **you must run it yourself first** (locally, in Colab, etc.), confirm it works, and save the file with the fresh outputs *before* committing. If you save a notebook with edited code but stale/old outputs, that's exactly what the published page will show — the build check won't catch the mismatch, since it never executes anything.
- **Page structure**: this is a [MyST Markdown](https://mystmd.org/guide) book. Regular Markdown works fine for most edits. Special call-out boxes look like this:
  ```
  :::{admonition} Title
  :class: tip
  Your text here.
  :::
  ```
- **Adding a new page**: create the `.md` or `.ipynb` file, then add it to the relevant `_toc.yml` (there's a root-level `/_toc.yml` that's the one actually used for the published site — LabManual's own `LabManual/_toc.yml` is a secondary config used only for generating a standalone Lab-Manual-only PDF, not the live site). If a page exists but isn't in `/_toc.yml`, it won't be built or published.

## If something looks broken

Open an issue, or just ask in a PR comment — you have write access, so you can always push a follow-up fix. Nothing here can accidentally take the live site down permanently; worst case, we revert a commit and the site rebuilds back to the last good version automatically.
